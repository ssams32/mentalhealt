# 07. 홈페이지 업체에 전달할 API 명세 요청서

- 작성일: 2026-11-12
- 발신: 이천시정신건강복지센터 (의뢰관리시스템 운영)
- 수신: 센터 홈페이지 개발·운영 업체
- 목적: 홈페이지(외부기관 의뢰접수·온라인 척도검사)에서 발생하는 데이터를
  센터 내부 Synology NAS의 의뢰관리시스템으로 자동 수신하기 위해 필요한 API 명세를 요청한다.
- 전제: 우리 쪽은 NAS 내부 백엔드가 외부 홈페이지 API에 HTTPS로 접속해 가져오는
  Pull 방식으로 설계했다. NAS 포트포워딩 없음, NAS 외부 공개 없음, 별도 중계 서버 없음.

---

## 1. 요청 개요

센터 홈페이지에서는 외부기관 의뢰접수와 온라인 척도검사 서비스를 제공하고 있다.
향후 홈페이지에서 발생하는 아래 데이터를 NAS 의뢰관리시스템으로 자동 수신하고자 한다.

- 외부기관에서 홈페이지를 통해 접수한 의뢰정보
- 홈페이지 이용자가 실시한 온라인 척도검사 결과
- 향후 추가될 수 있는 기타 접수 및 검사 데이터

이를 위해 홈페이지 측에서 아래 명세를 제공해 주시기 바란다.
명세가 확정되면 우리 쪽은 어댑터 설정 및 연결 모듈만 수정해 연동한다.

---

## 2. 요청 항목 (15개)

### 1) 운영 및 테스트 API 기본 주소

- 운영 API 기본 주소 (예: `https://api.example.com`)
- 테스트(스테이징) API 기본 주소 (운영 주소와 다른 호스트여야 함)
- 테스트 환경 이용 가능 여부와 이용 기간

### 2) 인증 방식 및 기관별 API 키 발급

- 인증 방식 (API 키 헤더 / Bearer 토큰 / OAuth / Basic 중 어떤 방식인지)
- API 키를 담는 헤더명 (예: `X-Api-Key`인지, 다른 이름인지)
- 기관별 API 키 발급 절차 (우리 기관 전용 키 발급 방법)
- 키 형식·길이 (최소 길이, 허용 문자)
- 키 재발급 절차 (새 키 발급 시 기존 키가 즉시 폐기되는지, 일정 기간 둘 다 유효한지)
- 키 폐기 절차 (폐기 요청 방법, 폐기 후 효력 발생 시점)

### 3) 신규 의뢰 목록 조회 API

- 엔드포인트 경로 및 HTTP 메서드 (예: `GET /api/v1/referrals`)
- 요청 파라미터 (페이지네이션, 조회 기간 필터, `since` 파라미터 지원 여부)
- 응답 형식 (목록 구조, `items` 배열 여부, 전체 건수 포함 여부)

### 4) 의뢰 단건 조회 API

- 엔드포인트 경로 및 HTTP 메서드 (예: `GET /api/v1/referrals/{id}`)
- 단건 조회가 없을 경우, 실패 항목 재처리 시 어떤 방식으로 다시 가져올 수 있는지

### 5) 척도검사 결과 조회 API

- 엔드포인트 경로 및 HTTP 메서드 (예: `GET /api/v1/assessments`)
- 요청 파라미터 (페이지네이션, 조회 기간 필터)
- 응답 형식 (목록 구조, 전체 건수 포함 여부)

### 6) 수신 완료 처리 API 제공 여부

- 수신 완료(ack)를 알리는 API가 있는지 (예: `POST /api/v1/referrals/{id}/ack`)
- ack API가 없을 경우, 이미 가져온 데이터를 다시 보내지 않는 기준 (조회 기간 필터로 충분한지)
- ack를 보내지 않은 데이터를 다시 전송하는지, 재전송 주기는 어떻게 되는지
- 실패 보고 API가 있는지 (예: `POST /api/v1/referrals/{id}/failed`)

### 7) JSON 데이터 구조 및 필수 필드

- 의뢰 데이터 JSON 스키마 (필드명, 타입, 필수 여부, 길이 상한)
- 척도검사 데이터 JSON 스키마 (필드명, 타입, 필수 여부)
- 의뢰 필수 입력값 목록 (이름, 연락처, 성별 등 — 어떤 항목이 항상 들어오는지)
- 선택 항목 목록 (없을 수 있는 항목)

### 8) 고유 접수 ID 형식

- 의뢰 고유 접수 ID 형식 (예: `hp_20261112_0001` 같은 형태인지, UUID인지)
- 척도검사 고유 제출 ID 형식 (의뢰 ID와 같은 체계인지, 다른 체계인지)
- 고유 접수 ID가 시간이 지나도 바뀌지 않는 안정적인 값인지 (재전송 시에도 같은 ID인지)
- 허용 문자·최대 길이

### 9) 날짜 및 시간대 규격

- 날짜·시각 형식 (ISO 8601인지, 다른 형식인지)
- 시간대 기준 (KST인지 UTC인지)
- 접수일시·실시일시·수정일시 등 각 날짜 필드의 의미

### 10) 페이지네이션 및 조회 기간 필터

- 페이지네이션 방식 (`limit`·`offset`인지, 커서 방식인지, `since` 파라미터인지)
- 한 번에 가져올 수 있는 최대 건수
- 조회 기간 필터 (시작일·종료일 지정 방식)
- 정렬 방식 (접수일 오름차순/내림차순)

### 11) 데이터 재전송 정책

- 이미 가져온 데이터를 다시 전송하는 조건 (ack 미수신 시, 일정 시간 후, 수동 요청 시 등)
- 재전송 시 고유 접수 ID가 동일한지
- 재전송 주기 (있다면)

### 12) API 요청 제한 및 권장 폴링 주기

- 분당·시간당 요청 수 제한 (rate limit)
- 제한 초과 시 응답 (HTTP 429 여부, `Retry-After` 헤더 제공 여부)
- 우리 쪽 기본 폴링 주기 1분(60초)이 허용되는지
- 권장 폴링 주기 (1분보다 길게 잡아야 한다면 권장값)

### 13) 오류 응답 규격

- 오류 응답 JSON 형식 (예: `{ "error": { "code": "...", "message": "..." } }`)
- 오류 코드 목록 (인증 실패·존재하지 않음·속도 제한·서버 오류 등)
- 재시도 가능 여부를 구분할 수 있는 기준 (어떤 오류는 다시 시도하고, 어떤 오류는 다시 시도하지 않는지)

### 14) 테스트용 인증키 및 데이터 제공 여부

- 테스트용 API 키 발급 가능 여부
- 테스트용 합성 데이터 제공 가능 여부 (실제 개인정보가 아닌 가짜 데이터)
- 테스트 환경에서 의뢰·척도검사 데이터를 직접 만들어 볼 수 있는지

### 15) API 변경 시 사전 공지 정책

- API 명세·주소·인증 방식이 바뀔 때 사전 공지 여부
- 공지 방법 (메일, 공지 게시판 등) 및 공지 기한 (변경 몇 주 전인지)
- 버전 관리 방식 (버전 번호가 있는지, 구버전 유지 기간이 있는지)

---

## 3. 우리 쪽 설계 전제 (업체가 참고할 사항)

- 수신 주기: 기본 1분(60초), 관리자 설정에서 변경 가능. 업체의 요청 제한에 따라 조정한다.
- 인증: 기관별 API 키를 NAS 환경변수 또는 Docker Secrets 파일로 관리한다.
  키를 홈페이지 측에 되돌려 보내거나, 우리 소스코드·설정 파일에 평문으로 저장하지 않는다.
- 중복 방지: 홈페이지에서 제공하는 고유 접수 ID를 기준으로 중복 수신을 막는다.
  같은 ID가 다시 오면 저장하지 않는다.
- 저장 후 ack: 데이터를 NAS에 정상 저장한 뒤에만 수신 완료 처리를 한다.
  저장에 실패한 데이터는 ack를 보내지 않고 다시 가져온다.
- 대상자 식별: 검사 결과와 의뢰정보는 대상자를 확실하게 식별할 수 있는 경우에만 연결한다.
  식별이 안 되면 임의로 연결하지 않고 따로 저장한다.
- 보안: 통신은 HTTPS만 사용한다. 로그에 개인정보·API 키를 남기지 않는다.

---

## 4. 답변 요청 기한 및 전달 방식

- 위 15개 항목에 대한 답변을 문서(메일 또는 별도 명세서)로 전달해 주시기 바란다.
- JSON 스키마는 예시 데이터 2~3건과 함께 보내 주시면 연동 작업이 빨라진다.
- 테스트용 키와 테스트 환경 주소가 준비되는 대로 알려 주시기 바란다.
